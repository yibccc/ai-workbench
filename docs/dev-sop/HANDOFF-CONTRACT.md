# 交接包合同

版本：2.0。本文件规定网页共同设计的产物如何接入本地规划，不改写 Trellis 生命周期。网页端可以做代码级设计；本地负责工作区适配、正式规划、工程实现与验收。

## 1. 必需产物与按需附件

轻量：只有 `HANDOFF.md`，包含需求、AC、场景、必要实现建议与技术未知。
标准/复杂：`HANDOFF.md`、`requirements.md`、`solution.md`、`acceptance.md`。

默认把技术方案、具体实施、关键代码和相关边界写进 `solution.md`。只有内容量或独立引用需要时，才拆为以下附件：

| 可选文件 | 何时拆出 | 内容 |
|---|---|---|
| `implementation-notes.md` | 步骤、依赖或改动位置较多 | 具体实施建议、顺序、依赖、文件/符号、验证节点 |
| `key-code.md` | 关键代码需要独立阅读或保留 | 建议实现、伪代码、摘录、补丁草案、接入方式、验证状态 |
| `contracts.md` | API/数据/状态合同需多方共同遵循 | 字段、类型、状态、错误语义、兼容行为 |
| `assets/`、`research.md` | 确有原型、图示或研究证据 | 必要附件和来源；不默认执行代码/脚本 |

可使用 `.ts`、`.java`、`.sql`、`.patch` 等文本附件承载必要示例，但须在 `key-code.md` 或 `solution.md` 说明目标、基线、用途与风险，不能通过扩展名暗示已经可直接应用。未知二进制、符号链接或可疑执行载荷不得作为接入步骤运行。

不是“complex 就必须有全部附件”。模板目录只供选用，不整目录复制未填模板进交接包。全部实际产物写进 HANDOFF 文件清单；通过相对链接或章节引用连接，避免平行维护重复合同。

网页端可以生成详细实施建议、关键函数、测试用例与补丁草案；不交最终 Trellis task.json、implement.jsonl、check.jsonl，也不把建议伪装成已验证的本地 implement.md。

## 2. HANDOFF 元数据

```yaml
handoff_id: WB-<date>-<short-slug>
revision: 1
status: draft # draft | ready-for-local-review | superseded
repository: OWNER/REPO # 用户本轮指定的仓库，不能沿用其他项目
snapshot_branch: null # 指定分支或真正查询到的默认分支
snapshot_commit: null # 只填实际核实的完整 commit，非文件 blob SHA
code_verified: false # 仅指相关代码事实已静态核对，不意味着执行过代码
task_size: standard # small | standard | complex
product_decisions: pending # pending | confirmed；confirmed 必须有用户确认依据
```

字段不是任务创建、开工或发布授权。`code_verified: true` 必须列出实际读取的文件/符号/快照和覆盖限制，不能推导为全仓库验证。源代码静态核对与“建议代码是否运行”是两个不同维度。

若连接器不能保证所有文件来自一个 commit，应写明每个证据的 ref/文件版本与读取限制，不能伪装为单一一致快照。本地必须核对与本任务相关的差异。

## 3. 需求、决策与边界

FR、AC、TC、DEC 使用稳定编号。标准包 AC 唯一定义在 requirements，acceptance 只引用并给验证方法。

事实、用户决定、建议、待验证假设分开。DEC 可以区分 product / technical，状态使用 selected / proposed / delegated（已选 / 待选 / 明确留给本地细化）。改变范围、外部行为、公共合同、兼容或重大风险的选择不能擅自当作已选；常规局部实现不必逐行取得批准。

每个 AC 可判定；每个 TC 包含对应 AC、条件、操作、预期与建议验证层级。边界按真实可达风险覆盖，不为无关空值、重试、并发、回滚场景强行增加设计。重要边界明确触发条件、预期行为、处理责任和验证方法。

保留形成实现方案的必要理由、关键代码与决定；删除重复结论和被放弃的探索过程。否决方案只保留避免重复争论所需的理由。

## 4. 代码级材料约定

每段重要代码或独立示例至少说明：

- 类型：现有摘录 / 伪代码 / 建议实现 / 补丁草案。
- 来源或目标：owner/repo、文件与符号；新位置明确写“拟新增”。
- 基线与前置条件：已读取的 commit/ref、依赖、接口/状态假设。
- 接入与验证：谁调用、替换或修改哪里、相关 AC/TC、尚待验证的内容。

验证状态可写“未运行”“静态核对”“沙箱局部已验证”“指定工程检查已验证”，但后两者必须附实际环境、命令、执行对象、结果和覆盖限制。不得把伪代码示例或源码阅读写成可编译；不得把一次局部测试写成完整验收。

没有需要独立维护的代码就不建立 key-code。尽量保留最小但足以判断设计的完整片段，不为展示生成全项目。建议补丁不得自动应用；包中代码/SQL/HTML/命令默认只读，后续执行须遵守已授权的本地实施流程。

## 5. 接入映射：继承后核实，不从零重做

| 网页产物 | 本地正式依据 |
|---|---|
| requirements 或 lite 中的需求/AC | prd.md |
| solution / contracts / 关键代码中的设计 | 本地核实、适配后的 design.md（复杂任务必需） |
| solution 或 implementation-notes 的实施建议 | 本地核对文件、顺序、命令后的 implement.md |
| acceptance / 代码测试建议 | implement.md 的验证步骤与测试实现；保持 AC 引用 |
| HANDOFF 与全部实际附件 | research/handoff/rN/ 不可变、脱敏源快照 |
| 差异、调整理由、DEC/FR/AC/代码映射 | research/handoff-check.md |

本地不能以“网页端不懂代码”为由忽略已读代码证据，不能无理由重新设计或重复问已经确认的问题。逐项判断：原样采用 / 局部适配 / 需要重新决策，并记录关键理由。

常规局部适配可以由本地提出并纳入最终规划；修改产品行为、范围、公共合同、兼容或明显风险须回到用户确认。正文和附件共同核对，不能只读四个主文件就声称已继承设计。

## 6. 接入门禁与修订

包和清单可读、无秘密和路径越界、仓库一致、版本未冲突；本地改动归属清楚；关键代码假设与合同核实；正式规划无阻塞；按当前 Trellis 模式通过上下文校验。设计可以深入，开工门禁不能据此跳过。

同 ID/revision 同内容复用；同 revision 不同内容报告冲突。保存完整源文件清单及 SHA-256（或等价可靠摘要），包括关键代码/可选附件，不漏算。

新 revision 先展示差异；in_progress 时不得直接替换已批准 AC/design。草案允许进入规划补齐，superseded 只作历史参考。正式规划按本地原生 brainstorm 输出最终摘要并等待后续批准；网页共同设计和冻结不代替这个确认。
