## 1. 要交付的闭环

每日重复模板 → 当日独立待办 → 关联或临时开始专注 → 净时间/15秒微休息 → 结束结算 → 当天工作记录 → 沿用日报/周报来源。

【用户已决定 / selected】采用上述轻量闭环，不另建计时应用，r2 新增独立“专注”业务工作区，不引入独立调度/消息服务。专注投入与任务完成分离；同一用户最多一段未结束会话；关闭页面/睡眠不保证准点声音。

本次修订依据：用户在 r1 后要求“专注新开一页吧，不和今日工作挤”。只替换页面职责和入口；数据模型、净计时、重复实例、微休息、结算/报告和恢复约束不因分页面改变。

## 4. 建议数据结构（拟新增，不是现有表）

| 对象 | 最小职责与候选字段 | 不可丢的约束 |
|---|---|---|
| 重复模板 `focus_routines`（名称待定） | owner、title、project_id?、weekdays、default_focus_duration、enabled、version、创建/更新时间。 | owner必须来自服务端；项目归属同用户；模板停用不级联删除历史。 |
| 当日待办实例（扩展现有 todo_items） | routine_id?、occurrence_date?，实例保存自身的任务内容。 | owner+routine+date 唯一且覆盖软删除，不能由过滤 deleted_at 的唯一索引允许补建。普通待办保持原行为。 |
| 专注会话 `focus_sessions`（拟新增） | owner、task_id?、project_id?、目标/标题快照、目标时长、提醒间隔、15秒引导配置、zone_id、状态、version、开始/结束、已结算计数、客户端请求键。 | 数据库保证每用户至多一个非终态；项目/任务同 owner；开始重试不重复建会话；历史标题/关联有依据。 |
| 计时区间 `focus_intervals`（拟新增） | session_id、kind、start/end、确认状态；必要的命令/提醒编号或同等审计信息。 | 同一会话区间不重叠、长度非负；FOCUS/BREAK/PAUSE/UNCONFIRMED 可区分；前端不能上报任意无限时长。 |
| 专注工作记录（扩展 work_records） | 新来源候选值 FOCUS_SESSION；focus_session_id、focus_date、净时长、休息时长、可选进展；原有 occurred_at。 | owner+session+date 至多一条；与结算同事务；不受 invalidateTaskCompletion 影响；不是通用手工可随意改时长的记录。 |

这是最小职责模型，不要求本地照搬所有候选列。若现有持久化结构能少建一张表满足同等约束，可局部适配并记录映射，不凭“可扩展”增加通用事件平台。

每日归属不能伪装成固定几点的截止时间。候选方案用 occurrence_date 记录重复实例归属，原 `due=TODAY` 等筛选继续按现有合同解释；需要改变现有筛选含义时必须返回用户确认。默认列表仍可看到新实例，不新增日历排程功能。

区间按半开范围 `[start,end)` 处理。先精确切日再汇总；显示舍入放到最后。保存业务时区用于解释历史分片，避免浏览器时区改变后错账；不新增每人选择时区的产品设置。

## 5. 状态、计时和异常恢复

下面状态名是建议，不是已存在枚举：

```text
IDLE --明确开始--> RUNNING
RUNNING --微休息到点且仍有目标剩余--> MICRO_BREAK
MICRO_BREAK --15秒正常结束/用户跳过--> RUNNING
RUNNING或MICRO_BREAK --明确暂停--> PAUSED
PAUSED --继续--> 对应未完成阶段
未结束状态 --确认到时或提前结束--> ENDED
未结束状态 --发现不可信时间缺口--> RECOVERY_REQUIRED
RECOVERY_REQUIRED --用户核对区间--> 恢复可计时状态或结束
```

PAUSED 必须保存暂停前阶段与该阶段剩余量，不能在暂停期间继续消耗15秒或产生休息到点事件。关闭本段提醒后，本段不再安排未来微休息；在休息中关闭/跳过只结算已经发生的引导时间。目标到期优先于下一微休息，避免净25分钟结束时多出无意义休息。

【建议】服务端保存时间锚点、区间与版本，前端仅推导当前显示。渲染回调、标签可见性和网络连接不是“用户专注”的证据。短暂刷新需要恢复会话，后台可见性变化也不能直接等价成用户离开；具体如何将长缺口转为待确认，留给本地基于支持浏览器实测阈值。

恢复时先读取账号的权威会话，不盲目重放缓存写入。只累加已经被可靠记录/用户明确确认的区间；不能用“当前时间−开始时间”补满睡眠期间，也不能假定每10分钟都已完成15秒闭眼。用户确认的缺口必须有明确起止位置，跨日才可复算，不仅填写一个无位置的分钟数。

**本地必须明确的可达边界**：刷新正好发生在微休息切换；已暂停会话长时间后重开；后台恢复时已超过目标时长；系统时间调整；网络断开时用户点击结束；会话失效后重新登录；新标签与旧标签争夺控制。相应测试引用 AC-002/003/005/006。

## 6. API与并发职责（候选接口，非已批准公共合同）

不提交完整 OpenAPI 或最终路由。建议在现有认证 HTTP 客户端下建立以下命令边界，本地可按现有命名细化：

| 能力 | 语义 |
|---|---|
| 模板读写/启停 | 读取当前账号模板；写入校验字段和版本，停用保留历史。 |
| 补齐当天任务 | 显式写命令，以服务器业务日期计算；不能在 GET 内藏写入，也不能由客户端指定其他 owner。 |
| 开始、读取当前会话 | 开始含幂等请求键和可选任务/项目；数据库争用下返回已存在会话或明确冲突，不新建第二段。 |
| 暂停、继续、休息到点/跳过、关闭提醒 | 版本/阶段受约束；旧标签不能覆盖较新状态；逻辑提醒以会话+序号唯一。 |
| 结束结算、可选进展补充 | 结束幂等；自动保存与可选进展编辑分离，用户关闭成果面板仍保留计时；任务完成另走现有操作。 |
| 确认恢复区间 | 校验区间在待确认缺口内、不重叠、与剩余目标不矛盾；重复提交不叠加用时。 |
| 当日汇总 | 按 owner+业务日期聚合结构化值；运行中显示与已结算部分分开。 |

身份错误沿用现有401/403/404和 ProblemDetail；跨用户 UUID 在泄露存在性/状态/版本前返回404；版本冲突以409反馈；字段无效不能写库。所有写入使用现有 CSRF 通道。不得为计时绕过会话失效。

【建议】跨标签/设备开始的唯一性由后端保障；可见性协调或 BroadcastChannel 只能减少 UI 噪音，不能替代数据库约束。提示主控至少覆盖同一浏览器多标签；若设计使用主控租约，主控换代后拒绝旧控制者事件。异常崩溃时音频的真实发出无法与数据库形成恰好一次事务，采用去重后的尽力而为提示，可能漏响但不编造已听见。

基础正确性只依赖现有后端与 PostgreSQL，不为专注新增 Redis业务权威或消息中间件。可优先HTTP恢复/命令响应；只有核实必要性才扩展现有实时事件种类，不能把目前仅 INPUT/REPORT 的事件实现当成已支持 FOCUS。

**结束事务示意（伪代码，未运行）**

```text
begin transaction
  用 authenticated_owner + session_id 锁定会话
  若已终结：返回已结算结果（不新建记录、不覆盖既有进展）
  校验版本、合法阶段、缺口确认和命令幂等性
  关闭/核对计时区间；按业务时区切分并计算每日净时长
  原子写入会话结算、区间与每日日分片工作记录
commit
事务后通知刷新；通知失败可用HTTP恢复，不回滚已提交事实
```

类型：伪代码；目标：拟新增专注 Service 实现的结束命令，沿用当前仓库 service.impl 事务边界。前提：本地确认所有权、区间和唯一约束。关联 AC-004/005/006，TC-009/010/013；不对应可直接编译类或补丁。

## 7. 当天记录与报告适配

FOCUS_SESSION 作为候选新来源沿用现有 work_records 入口，但以 session/date/时长字段承载事实。严禁只往 content 塞“25分钟”，否则无法可靠汇总、去重、撤销任务完成时分类。

日/周候选记录查询目前都会把有效 work_records 读入，因此需要检查 ReportSourceRow、来源展示、生成输入组织及模型输出限制。快照建议补齐 sessionId、focusDate、duration、breakDuration、progress 和 taskId；字段名称待本地对齐。不得每个微休息独立成为报告来源。

围绕同一个任务的投入与完成应在来源组织/确定性数据整理阶段关联，不只靠一句模型提示去重。保留原始可追溯证据，不删掉任务完成事实来消除重复。专注计时不触发付费模型；用户主动生成报告仍沿用原有调用路径。新增事实只影响之后的新报告，不后台改写旧版。

一般记录编辑/删除的实际保护代码尚未完整读取。专注来源必须有专门受控的进展修改入口或等价处理，不能被误判为 TASK_COMPLETION，也不能由通用手工接口任意改时长。任意历史用时改写/删除不在本轮范围。

## 8. 独立专注页接入与代码附件（r2）

### 8.1 页面分工与已确认冲突处理

【用户已决定】增加工作台内独立专注页，不把计时与今日工作正文挤在一起。导航建议顺序为“工作记录 / 待办任务 / 专注 / 工作汇报 / 项目管理”；保留原四项相对次序和 `records` 默认入口。r2 明确替代 r1 DEC-006 的布局约束。

【已核实事实】当前 `navigation.ts` 和前端 `directory-structure.md` 仍列四个业务入口。新增专注与这段现状描述不同，由用户本次要求解决该产品选择。网页端不修改该规范；本地获准实施后同步“新增 focus”对应的规范、导航测试与辅助用户管理说明，不覆盖整份 AGENTS/spec，也不把管理员辅助页误并成业务页。

【建议】专注页内采用“专注计时 / 重复任务”两个标签。计时区展示目标、净时间、暂停/结束和提醒；今日净计时汇总也归属此页。重复规则的编辑可以继续用辅助抽屉，但当前专注本身是完整页面，不是抽屉。所有开始入口汇聚同一会话控制逻辑，不能造第二套计时器。

工作记录页保留原输入和记录列表；已结束专注只作为一种可追溯记录显示，不新增专注汇总大卡、计时器或重复设置。专注结束只触发相关数据刷新，不自动跳转到工作记录，也不调用手工 onSaved 改掉用户正在查看的日期。查看记录由用户正常导航完成。

会话与音频生命周期仍处于 retained pages 之外、账号根之内。隐藏专注页不能卸载计时权威状态；手机/桌面重复渲染控制栏也不能重复启动音频控制者。微休息为账号级全局引导，不依赖隐藏页面的 Toast。当前会话是“会话”，登录会话是“认证状态”，不得混淆并用自动轮询续期登录。

### 8.3 页面行为与辅助交互

待办入口先带入目标、任务/项目和默认时长到专注页，明确开始后才创建会话。有未结束会话时返回当前会话，不覆盖目标或默默开始第二段。离页后紧凑入口仅含状态/剩余/暂停或继续/返回；不能在记录正文重建完整功能卡片。

手机用独立页面纵向布局，全部控制正常滚动可达；不靠原来的全屏专注抽屉承载计时。重复规则和结束进展仍可使用辅助抽屉；关闭这些辅助层不隐含结束正在进行的会话。真实工程保留键盘访问、焦点恢复、草稿防丢、原分页/日期语义与已有未保存报告提示。

### 8.4 可审查代码与验证范围

`assets/focus-prototype.html` 是**建议UI代码**，含原生 HTML/CSS/JavaScript，自包含，不发业务请求、不写浏览器持久化、不播放声音、不运行真实倒计时。示例全部合成；按“开始”仅进入固定数字的状态展示。它不是 React 补丁，不要覆盖 App.tsx 或 styles.css。

为了便于审阅，此原型默认打开专注示例；这不改变正式工作台的默认 records 入口。原型中的记录、待办、报告、项目只是本次导航/草稿展示所需的最小示意，不是这些页面的完整再实现。通过原型测得的导航/DOM状态保留不证明生产持久化、恢复、多标签互斥或音频可靠。

## 9. 建议本地适配顺序

1. 只读核对 HANDOFF、当前HEAD、工作区改动、合同与相关spec；核查本包每项映射，必要变更带证据返回用户。经授权进入本地正式规划。
2. 在设计中固定区间计时、异常阈值、命令幂等、所有权和记录日分片，明确新增来源兼容；选择下一迁移版本和约束。
3. 先完成数据/服务/日期/并发确定性验证，再把模板生成接到当天入口；禁止改变既有截止筛选语义。
4. 在账号级根部接入会话与声音控制，新增独立 FocusPage 和导航/顶栏接入，记录页只适配来源展示；核对草稿/刷新/多标签/换号。
5. 联通专注记录、日汇总和报告快照/输入，验证任务重开不抹掉用时与版本不回写。
6. 按 acceptance 的场景，运行隔离数据库与确定性模型回归，补浏览器声音/恢复人工验证及发布/回退演练。正式规划获得批准后才实施。

以上是建议顺序，不是最终 implement.md；未执行其中任何生产步骤。

## 10. 兼容、风险与回退

新增来源值会影响旧版后端枚举反序列化、约束和前端来源分支。候选上线顺序：先使读取端兼容新结构/来源，所有实例确认兼容后再开放新写入。是否允许混合版本部署待本地核对；未验证前不承诺滚动降级。

保留已应用迁移；新迁移只做必要扩展。历史普通待办、手工记录、任务完成事实不批量改写。新项目关联必须遵循有效项目和同 owner 约束；模板生成遇到归档项目应报告明确阻塞，不能静默换成未分类。开始后才归档的会话需要保留已有合法关联，如何通过专用结算实现应在本地核实，不能开放通用新增记录绕过限制。

回退优先关闭新入口/新写入并保留已生成数据，使用仍认识新来源的兼容读版本；不要直接把不认识 FOCUS_SESSION 的旧程序连到新数据上。全量恢复备份须单独授权、说明新数据损失并在隔离环境演练；不删除专注历史、不回滚旧迁移校验和、不混淆“关入口”和“完成回滚”。具体开关形式和版本顺序是 delegated。
