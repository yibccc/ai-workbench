## 1. 产品目标

为个人提供一个能够持续使用的工作记录与待办工作台，打通：

**自然语言记录 → 工作记录与待办 → 完成待办并留下成果 → 当天汇总 → 周报草稿 → 编辑、复制并提交。**

第一优先级是降低记录和整理成本，并通过真实使用观察时间节省；兼顾技术学习和求职展示。目标是在两个自然周内交付核心流程，具体进度以每日验收结果为准。

### 成功标准

| 编号 | 目标 | 观察方式 |
|---|---|---|
| G01 | 形成持续记录习惯 | 验收期连续 5 个工作日使用工作台留下真实记录 |
| G02 | 完成一次完整周报流程 | 从真实记录生成周报，经用户修改后可以复制提交 |
| G03 | 能观察到时间变化 | 用户记录一次现有周报整理耗时，再记录工作台生成及修改耗时，比较变化 |
| G04 | 基础数据可靠 | 修改、撤销、重试、完成与重开后，没有丢失原文、重复成果或错误状态 |
| G05 | 能解释技术设计 | 交付启动说明、架构说明和一组可复现的核心场景 |

不预先宣称节省百分比；G01—G03 的实际结果在试用后记录。使用观察先通过验收记录完成，不新增统计看板。

## 2. 用户与使用环境

- 第一版为用户本人使用的单人工作台。
- 在 Windows 11 本机运行，通过浏览器访问。
- 主要输入为用户手写或粘贴的自然语言文本。
- 模型使用 DeepSeek 官方 API，通过 OpenAI 兼容接口接入。
- 时区为 Asia/Shanghai；展示工作发生日期和实际录入时间。
- 两周内优先完成核心流程，架构保留后续部署服务器的可能。

## 3. 已确认范围

| 编号 | 功能 | 已确认行为 |
|---|---|---|
| F01 | 统一输入 | 一个输入框接收工作记录和待办，AI 自动拆分并保存，支持修改和撤销 |
| F02 | 工作记录 | 保存工作内容，支持补充实际结果和补录历史日期 |
| F03 | 待办 | 标题、备注、可选截止日期、优先级、项目；新增、编辑、完成、重开和删除 |
| F04 | 项目分类 | 记录与待办共用项目；新项目手动创建，AI 仅匹配已有项目，否则未分类 |
| F05 | 完成记录 | 完成待办自动生成关联记录；重开后保留历史，但关联记录不再计入当前已完成成果 |
| F06 | 当天汇总 | 用户手动点击生成，可补充记录后重新生成 |
| F07 | 周报 | 本周完成、进行中与阻碍、下周计划；可编辑和复制 |
| F08 | 草稿保护 | 重新生成保留旧稿，不覆盖已编辑内容 |
| F09 | 失败恢复 | 先保留输入原文，AI 失败后可以重试 |
| F10 | 内容依据 | 报告基于已有记录，区分完成事实、工作进展和未来计划 |

默认优先级为高、中、低三档，未指定时为中。周报默认按周一至周日生成。

第一版不包含通用聊天、个人知识问答、知识库或 RAG、文件解析、外部应用同步、定时生成与通知、多用户协作、重复待办、自动对外提交报告。这些是范围边界，不进入本轮验收。

## 4. 典型使用流程

### 4.1 随手录入

用户输入：“今天修复了登录问题，明天写接口文档。”

1. 后端先保存原文及本次提交标识，前端展示处理状态。
2. AI 提取一条工作记录和一条待办。
3. 工作记录的发生日期为当天，待办截止日期按“明天”解析。
4. 后端校验提取结果、日期和项目归属，再保存业务数据。
5. 前端展示已生成条目，用户可以修改或撤销。

该例只是验收样本，不限制用户必须采用固定句式。一条输入可以包含多条记录、多个待办，也可以只包含一种内容。

### 4.2 完成待办

1. 用户勾选待办完成。
2. 系统同步创建关联的完成记录。
3. 用户可以补充完成结果，例如“文档已评审，剩余两个示例另建待办”。
4. 当天汇总和周报读取该记录。
5. 用户重新打开待办时，当前完成记录失效，但操作历史保留。

### 4.3 晚间回顾与周报

1. 用户补录遗漏的工作内容，并修正日期或项目。
2. 手动生成当天汇总，检查成果、进展和未完成事项。
3. 选择一个自然周，生成固定三段结构的周报。
4. 核对来源，编辑文本，复制到实际提交渠道。
5. 补充记录后再次生成时产生新草稿，原稿仍然可访问。

## 5. 页面与交互建议

本节是初版页面建议，可在每日体验中调整布局。

| 页面 | 主要内容 | 主要操作 |
|---|---|---|
| 今日工作台 | 快捷输入、处理状态、今日记录、到期与逾期待办、当天汇总 | 录入、补记、改错、完成待办、生成汇总 |
| 待办 | 所有待办，按状态、项目、优先级、截止日期筛选 | 编辑、完成、重开、删除 |
| 周报 | 选周、三段正文、来源记录、历史草稿 | 生成、编辑、保存、复制 |
| 项目管理 | 项目名称和归档状态，可采用轻量弹窗或页面 | 手动创建、改名、归档 |

输入区应始终容易找到。AI 处理状态使用“处理中、已保存、处理失败”等直接描述，不向用户展示内部框架名或模型调用协议。

## 6. 业务规则与初版实现细节

本节将已确认规则具体化。批量撤销的冲突处理、归档方式和草稿存储形式属于实现建议，尚未经过真实使用验证。

### R01：原文、时间与事实

- 原文与拆分后的条目建立关联，修改业务条目不覆盖原始输入。
- 工作发生日期用于日报、周报范围筛选；录入时间用于追踪补记。
- “昨天、明天、本周”等相对日期，以该次输入的本地时间为基准；失败重试沿用同一基准。
- 无明确日期的工作记录默认当天；无明确期限的待办不自动添加截止日期。
- 日期无法可靠解析时保留原话，提示用户补充，不自行编造。
- AI 识别文本中的明确成果，不把计划、尝试或部分进展当作已完成。

### R02：项目与优先级

- 项目由用户创建，AI 只能选择当前已有且未归档的项目。
- 匹配不到或多个项目同样可能时归为“未分类”，允许用户修改。
- 项目改名保留同一标识；归档不删除历史记录，归档项目不参与新输入自动匹配。
- 高、中、低分别对应 HIGH、MEDIUM、LOW；未明确表达紧急程度时默认 MEDIUM。
- 模型返回未知项目或未知优先级时，后端采用未分类或默认优先级，并保留可修改提示。

### R03：完成、重开与重复操作

- 待办完成与自动完成记录在同一数据库事务中写入。
- 重复点击完成或网络重试不会生成重复的当前完成记录。
- 重开撤销当前完成记录的有效性，不物理删除历史。
- 再次完成后只有一个当前有效的自动完成记录；它以本次完成时间参与当前统计，历史状态变化可追踪。
- 删除已完成待办时，其自动完成记录同步失效；单独手写的工作记录不会被连带删除。
- 自动完成记录的状态随待办变化。用户需要撤销完成事实时，通过重开待办操作；记录中补充的结果保留在历史中。
- 若用户另行录入了与待办相同的成果，报告应合并表述并关联多个来源，不静默删除用户原始记录。

### R04：修改与撤销

- 修改支持内容、日期、项目，以及待办优先级、截止日期。
- “撤销本次录入”针对同一次输入生成的整批条目，按一次事务处理。
- 若生成条目尚未被后续编辑、完成或单独删除，可以整体撤销。
- 若已发生后续变更，整体撤销返回明确的冲突说明，用户可逐项调整，避免覆盖后续成果。
- 原文和撤销状态保留；被撤销条目不参与新生成的汇总。
- 重复撤销同一次输入返回相同结果，不重复执行。

### R05：AI 失败与重复提交

- 保存原文成功后，AI 超时、返回空内容、格式错误或业务校验失败，都不能丢失原文。
- 一次输入的业务条目全部保存或全部不保存，避免出现半批结果。
- 同一次请求重发、失败重试或并发重试，最终只产生一批业务条目。
- 主动提交相同文本属于新的输入，不以文本相同为理由直接丢弃。
- 前端明确展示失败和重试入口；成功保存后刷新页面仍能读取条目。
- AI 失败不影响已有待办的编辑、完成、重开，也不影响已有报告的读取。

### R06：日报与周报范围

- 日报使用所选本地日期；默认当天。
- 周报默认自然周，包含周一 00:00 到下周一 00:00 之前的工作记录。
- 数据库可以统一保存 UTC 时间，查询边界由 Asia/Shanghai 转换，避免跨日偏移。
- “本周完成”只写明确完成的工作成果和有效自动完成记录。
- “进行中与阻碍”来自本周实际记录的进展、问题，以及生成时仍未完成且本周有活动的待办。
- “下周计划”来自明确安排在下一周的待办和记录；无期限待办不自动成为下周承诺。
- 某段没有依据时使用“暂无记录”或“暂无已安排计划”，不补造内容。
- 对历史周期重新生成时，使用该周期内的记录及生成时的有效状态，不声称重建任意历史时刻的数据库状态。

### R07：报告来源与草稿

- 每次生成保存周期、生成时间、正文，以及所使用来源的内容快照和标识。
- 每条生成要点能够找到对应来源；没有来源的完成事实不能作为生成结果直接保存。
- 用户手工补充的文本允许保存，并与 AI 生成部分的来源关系区分，不能伪造来源。
- 编辑需要明确保存；重新生成形成新版本，旧版本正文和来源快照保持不变。
- 来源随后修改、删除或失效，不自动改写旧报告；查看旧报告时可以提示它是生成时的快照。
- 复制默认输出报告正文，来源信息在工作台内查看。

## 7. 数据对象建议

这是概念模型，不是已经建成的数据库。

| 对象 | 职责与关键内容 |
|---|---|
| InputEntry | 原文、提交标识、日期解析基准、处理状态、错误信息、撤销状态 |
| Project | 稳定标识、名称、归档状态 |
| Task | 标题、备注、截止日期、优先级、状态、项目、来源输入、并发版本 |
| WorkRecord | 工作内容、发生时间、项目、来源输入或待办、有效性、并发版本 |
| TaskEvent | 完成、重开、删除等状态变化及当时关联记录的快照 |
| Report | 日报或周报、时间范围、正文、来源快照、生成与编辑时间、版本关系 |

工作记录表达发生了什么，待办表达准备做什么。两者可以关联，但不能互相替代。

## 8. 技术约束

| 部分 | 已指定技术 | 第一版职责 |
|---|---|---|
| 前端 | React、Vite | 表单、列表、报告编辑与状态反馈 |
| 后端 | Java、Maven、Spring Boot 3 | 业务规则、事务、校验和 HTTP API |
| 数据访问 | MyBatis | 显式 SQL 与对象映射 |
| 主存储 | PostgreSQL | 原文、业务条目、状态历史、报告与来源快照 |
| 辅助存储 | Redis | 短期请求去重与模型调用并发控制；持久化正确性由 PostgreSQL 保证 |
| AI 编排 | AgentScope Java | 结构化提取、日报与周报生成 |
| 模型服务 | DeepSeek 官方 API | OpenAI 兼容接入，模型名与调用参数可配置 |

采用一个后端应用，按业务模块划分。AI 输出经过业务层校验后再写库，模型不直接执行数据库写入。

关键凭据仅由后端配置读取，不放入前端构建产物。第一版服务按本机访问配置；服务器部署需要另行补齐访问控制。

AgentScope Java、Spring Boot 3 与 DeepSeek 的具体版本组合需先完成最小验证。此项是开发计划中的首个技术关卡，不是已验证完成的结论。

## 9. 验收场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A01 | 一句话同时描述成果与未来任务 | 分别生成记录和待办，保留原文，日期正确 |
| A02 | 输入提到未知项目，未指定优先级 | 项目为未分类，优先级为中，不自动新建项目 |
| A03 | 补录昨天工作后重试解析 | 工作发生日期仍为昨天，不随重试日期漂移 |
| A04 | 撤销一批未被再次编辑的输入结果 | 整批条目撤销，原文保留，新报告不引用该批条目 |
| A05 | 修改条目后再尝试整批撤销 | 明确提示存在后续变更，已修改内容保持完整 |
| A06 | 完成、重复完成、重开、再次完成 | 当前完成事实数量依次为 1、1、0、1；状态历史可查 |
| A07 | AI 超时、空输出、非法结果，随后重试 | 原文不丢失，成功后只保存一批合法结果 |
| A08 | 按项目与优先级筛选待办，编辑并刷新 | 筛选、状态与持久化结果一致 |
| A09 | 生成日报 | 只使用选定日期的记录，区分成果、进展和计划 |
| A10 | 生成周报 | 固定三段，无依据不补造；无期限任务不擅自成为下周计划 |
| A11 | 编辑旧周报、修改来源，再重新生成 | 旧稿与旧来源快照保留，新稿反映当前来源 |
| A12 | 查阅报告某个生成要点 | 可以定位来源；无来源的用户补充文本不会伪装成有来源的 AI 结论 |
| A13 | 本机服务重启 | 原文、待办、记录和报告仍可读取；失败输入可以继续重试 |
| A14 | 连续真实使用并完成周报提交 | 满足 G01、G02，并记录 G03 的实际耗时对比 |

AI 内容质量通过固定样本和用户真实验收共同判断；自动化检查主要验证结构、来源标识、状态转换、范围和持久化。

## 10. 后续迭代入口

核心流程稳定后，再根据真实使用中最耗时的环节选择下一项能力。定时汇总、通知、重复待办、个人记录问答和外部数据接入均作为候选，不计入这次两周计划。
